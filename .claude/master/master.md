# CubeNest — 마스터(개요·공통)

> **버전:** v1.9.1
> **상태:** 확정 (기준 문서)
> **최종 수정일:** 2026-08-21
> **문서 성격:** 프로젝트 전체가 공유하는 **불변 원리와 공통 규칙을 단일 출처로** 모은 상위 문서.
> **원칙:** 공통되는 것은 여기에만 정의하고, 각 페이지 문서는 "마스터 ○장 참조"로 가리킨다(페이지 문서에서 재정의 금지).
> **문서 안정성:** **3·4장은 [불변]** — 프로젝트의 중심 축이라 거의 바뀌지 않는다. 반면 2·6·7·9장(사이트맵·배포·데이터/인증/결제·로드맵·인덱스)은 프로젝트와 함께 갱신되는 가변 영역이다.
> **재구성 주의(v1.1.0):** 본 파일은 프로젝트에 파일로 마운트되지 않아 프로젝트 지식에서 재구성했다. **[불변] 3·4장은 원문과 대조**해 차이가 없는지 확인할 것(변경 의도 없음).

## 1. 제품 개요 · 타깃 · 브랜드

**CubeNest(큐브네스트)**는 3D 격자에 쌓기나무(단위 정육면체)를 쌓고 여러 방향에서 관찰하며 개수·부피·겉넓이를 배우는 웹 학습 도구. 태블릿·휴대폰 우선. 브랜드 워드마크는 브라우저 언어에 따라 한국어 '큐브네스트' / 그 외 'CubeNest', 부제 '쌓기나무 3D 학습'.

**대상 (v1.9.0 갱신 — 초6 1개 학년 → 만 8~13세):** 한국 교육과정 기준 **연령 스테이지**를 난이도의 최상위 축으로 둔다. 스테이지가 **열리는 유형·개수 밴드·높이·격자·가림 허용**을 먼저 정하고, 하/중/상/최상은 그 안의 **상대** 난이도다.

| Stage | 만 나이 | 학년 | 역할 | 출시 |
|---|---|---|---|---|
| S1 | 6~7 | 초1~2 | 쌓아 보고 세기 | ⏸ 보류(유형이 `count` 하나 — playground가 이미 제공) |
| S2 | 8~9 | 초3~4 | 교과 공백 구간 — 공간감각·선행 입구 | ✅ |
| S3 | 10 | 초5 | 겨냥도 읽기(겨냥도를 처음 배우는 학년) | ✅ |
| **S4** | **11** | **초6** | **6-1 부피·겉넓이 / 6-2 공간과 입체 — 제품의 원점** | ✅ **기본값** |
| S5 | 12~13 | 중1~2 | 심화·복습 | ✅ |

> 스테이지별 밴드·유형 개방·출제 형식의 **정본은 `cubenest_난이도_재설계`(§9)** 이고, 마스터는 축의 존재와 기본값(S4)만 고정한다. 해외(미국·싱가포르·태국) 진출은 **후순위** — 조사 결과는 `cubenest_연령별_국제_난이도설계`에 보류 보관.

**경로 규칙 (프로젝트 페이지의 하위경로 함정):**
- 이 사이트는 `/cubenest/` 하위경로에 서빙되므로, **루트 절대경로(`/playground/`)는 `smallhamsters.github.io/playground/`로 새어 나가 깨진다.** 링크·자산은 **상대경로**를 쓴다. 예: 랜딩→도구는 `href="playground/"` (O), `href="/playground/"` (X).
- 도구를 루트 → `/playground/`로 내리면 **기능 변화 없이 경로만** 바뀐다. 공유 링크(`?m=`)는 `location.pathname` 기반이라 자동으로 `/cubenest/playground/?m=…`가 되어 코드 수정 불필요.
- **페이지별 메타는 자기 URL로:** 각 페이지의 `og:url`·`canonical`은 그 페이지의 실제 절대 URL로 지정한다(예: 도구는 `…/cubenest/playground/`). `og:image`·`twitter:image`는 공용 `assets/img/cubenest-og.png`를 절대 URL로 공유.

## 3. [불변] 공통 토대 (데이터 모델 · 규칙)

- **3.1 데이터 모델:** 상태는 3D 격자 `(x,y,z)`의 채움/비움. 채운 칸 1개 = 쌓기나무 1개.
- **3.2 기준 방향·축 대응:** 앞 = +z, 옆(오른쪽) = +x, 위 = +y. '옆'은 오른쪽 면.
- **3.3 중력 규칙(뜬 나무 비허용):** 공중에 뜬 나무 불가. 추가 시 뜨는 자리 차단, 받침 나무 삭제 차단.
- **3.4 격자 크기:** 기본 3×3×3, 축별 독립, 최대 10. 축소 시 밖으로 나가는 나무가 있으면 축소 차단.
- **3.5 투영 방식:** 자유·정렬 보기 모두 직교(orthographic). 원근 폐기.
- **3.6 편집·관찰 분리:** 편집(추가·삭제)은 **자유 3D 보기에서만**. 위·앞·옆 정렬 보기는 관찰 전용.

## 4. [불변] 모양 수학의 중심 원리 〔단일 출처〕

> playground·worksheets·quiz가 **모두 이 원리만 사용**한다. 각 페이지에서 다시 정의하지 않는다.
> 모양에 관한 모든 계산·판정이 여기서 나오는 **중심 축**이며, 아래 다섯 층(직렬화 → 정방향 → 투상 → 역방향 → 문제 스키마)으로 이룬다.

### 4.1 순수 모양 직렬화 (`?m=`)
- 내용: `[버전, gx, gy, gz, edge] + 채운 칸 비트마스크`(셀 index `x·gy·gz + y·gz + z`), URL-safe base64.
- **모양·격자·모서리만 담는다. 문제 유형·정답 등 메타는 절대 섞지 않는다**(섞으면 공유 링크 포맷이 오염됨).
- 역직렬화 시 격자·모서리 1~10, 버전 검증. 실패 시 무효 처리.

### 4.2 정방향 계산 (모양 → 값)
- 개수 = 채운 칸 수. 부피 = 개수 × (모서리 길이)³.
- 맞닿은 면 쌍 = 서로 인접(+x·+y·+z)한 채운 칸 쌍의 수.
- **노출면(정확식) = 6 × 개수 − 2 × 맞닿은 면 쌍.** 구멍 유무와 무관하게 항상 정확.
- 겉넓이 = 노출면 × (모서리 길이)². **바닥면 포함.**
- **`2 × (위 + 앞 + 옆)` 표기 — 또 하나의 정확식:** 여기서 위·앞·옆은 각 방향에서 **실제로 드러난 면의 수**(그림자/실루엣 넓이가 아님)다. 이렇게 정의하면 **구멍 유무와 무관하게 항상 정확**하며 위 정확식과 **같은 값**이다. playground UI의 노출면 표기가 이 형태이고, 초등 학습에 직관적이라 **교육·설명용 표기**로 쓴다. 한편 `6 × 개수 − 2 × 맞닿은 면`(count−pairs) 형태는 **겉넓이 해설의 '대안 표기(다른 해설)'로 항상 허용**한다(v1.5.2 완화 — 종전 '오목 문제에만 허용'을 대체). 단 **`2×(위+앞+옆)`이 항상 주(primary) 표기**이고, 대안은 아이 친화적인 '다른 방법으로 풀기'로 제시하며 'count−pairs/정확식' 같은 날 용어를 전면에 내세우지 않는다. (이는 표시 정책일 뿐, `6N−2쌍 == 2×(위+앞+옆)` 등식 자체는 불변. playground에서 떨어진 두 칸의 노출면이 12로 정확히 나옴이 확인됨.)
- **출제 범위:** quiz·worksheet는 **연결된(구멍 없는) 모양만** 출제한다. (계산 자체는 위 두 식으로 어떤 모양이든 정확하지만, 문항은 연결된 모양으로 한정한다.)
- **오목(노치) 판정 — 겉넓이 난이도 축 (v1.5.0):** '오목'은 **`노출면 > 2 × (위+앞+옆 실루엣 넓이)`** 인 모양으로 정의한다(등호면 오목 없음). 여기서 실루엣은 4.3(b)의 투영 그림자다. 이 지표는 **실루엣이 못 잡는 숨은 면(노치)**을 정확히 골라내며, 그것이 `2×(위+앞+옆)` 직관을 깨는 난이도 동인이다. **O(N)** 로 판정 가능하고 quiz·worksheets 생성기가 **공용**으로 쓴다.
  - *유의(용어):* 이 판정은 '숨은 면을 만드는 노치'를 잡는 것이라, **L자 같은 오목 모서리는 '오목 없음'으로 분류**된다(어느 축에서도 숨는 면이 없어 직관 유지 = 저난이도가 맞음). '모든 기하학적 오목'과는 다르다.
  - **겉넓이 출제 난이도:** 오목 여부를 축으로 삼는다 — **하·중 = 오목 없음 / 상 = 혼재(전이) / 최상 = 오목 있음.** level별 givens·세부 밴딩(격자·밀도·유형 고유축)은 각 모듈·**문제 분류 체계**(`cubenest_remap` 유형·난이도 스펙, §9) 소관.

### 4.3 투상 (모양 → 그림) — **두 종류로 구분**
교과가 두 가지를 다르게 쓰므로 정의도 나눈다.
- **(a) 위에서 본 높이 지도:** 각 `(x,z)` 칸의 최고 높이(쌓인 층 수). 개수가 **유일하게** 확정됨 → '위에 수 쓰기' 유형.
- **(b) 세 방향 실루엣:** 위/앞/옆 각 방향의 채움 그림자(불리언 격자). 위 = XZ 투영, 앞 = XY 투영, 옆 = ZY 투영. 높이가 **확정되지 않아** 개수에 범위(최소·최대)가 생김. ※ 여기서의 '실루엣'(투영 그림자)은 4.2 노출면에서 쓰는 '위·앞·옆 = 드러난 면 수'와는 **다른 개념**이다.

### 4.4 역방향 (제약 → 모양 집합) — 최소·최대·은면
- **중력 준수(3.3, 확정):** 최소·최대 모두 **뜬 나무 비허용**. 따라서 각 기둥은 바닥부터 연속으로 쌓이고, 모양은 **높이 지도 `h(x,z)`**(각 칸의 층 수, 0=빈칸)로 완전히 표현된다. 이는 교과의 표준 모델(위에서 본 모양 + 높이)과 일치한다.
- 이 표현에서 세 실루엣은: **위** = {`h ≥ 1`인 칸}, **앞** = x별 최대 높이 `max_z h(x,z)`, **옆** = z별 최대 높이 `max_x h(x,z)`.
- **최대 모양:** 위에 속한 각 `(x,z)`에서 `h = min(앞높이[x], 옆높이[z])`. 앞·옆 실루엣을 넘지 않는 최대치.
- **최소 모양:** 위의 모든 칸을 최소 1로 두되, 각 **앞높이·옆높이(봉우리)를 실제로 실현**하는 데 필요한 '높은 칸'만 최소로 배치한다(덮개/배정 최적화 → **결정 2**).
- **자유 칸(은면):** 최대 − 최소 = 숨은 나무의 자유도. 교과의 "보이지 않는 쌓기나무"(안 보이는 나무) 개수가 여기서 나온다(= 자유 칸 = 최대−최소).
  - *주의(quiz 정합):* 은면(=자유 칸, 최대−최소)이 quiz의 **'가림(occlusion) 유형'과 항상 일치하는 것은 아니다.** 실무상 quiz에는 겨냥도에서 다른 큐브에 가려 안 보이는 나무를 다루는 등 가림 관점이 필요한 문제가 있어, 그 관점은 자유 칸 정의와 정확히 대응하지 않을 수 있다. 문제마다 어느 관점(자유 칸 / 가림)인지 명시해 쓴다.
- **채점 원칙:** "만든 모양의 위·앞·옆 == 목표인가", "개수 == 최소/최대인가", "은면 포함 최대가 맞는가"로 판정한다(정답이 여럿이라 저장된 단일 모양과의 일치로는 채점 불가).

> **결정 1 (확정) — 최소·최대는 중력(3.3)을 준수한다(뜬 나무 비허용).** 위의 높이 지도 모델이 그 반영이며, playground의 '모양 만들기'도 동일 모델을 쓰므로 별도 모드가 필요 없다.
> **결정 2 (확정) — 최소 개수는 정확 계산으로 구하며, 정답 값은 유일하다.** 위·앞·옆이 문제에서 주어진 입력이고 격자가 10 이하이므로, '앞·옆의 봉우리를 어느 칸에서 실현할지' 고르는 작은 덮개 문제로 최소를 정확히·빠르게 구할 수 있다. 최소 **배치**는 여럿일 수 있으나 **최소 개수(값)는 유일**해 정답지에 모호함이 없다. *전제:* 주어진 세 뷰는 실제 모양에서 뽑아 항상 서로 모순이 없다 — 훗날 사용자가 뷰를 임의로 입력하게 되면 뷰 정합성 검사를 이 절에 추가한다.

- **버전·캐시:** 각 모듈은 `CubeNest.core.VERSION` 등 버전 상수를 노출한다. **모듈 버전은 §9 인덱스에 개별 등재**하고, API·테스트 상세는 **`cubenest_모듈_명세서`가 정본**이다. 갱신 시 브라우저·GitHub Pages 캐시 무효화를 위해 필요하면 `?v=<버전>`(또는 파일명 버전)을 붙인다.
- **테스트(필수):** core는 정답·채점의 단일 출처라 파급이 크다. **회귀 테스트 케이스를 동반**한다 — 예: 떨어진 두 칸 겉넓이 12, 최소·최대 값의 유일성, 은면 예시(4.4).
- **오너십:** core·viewer의 정본은 현재 playground가 보유 → **playground가 추출·유지**(초기). 단 **프로젝트 공용 자산**이며 변경은 **단일 지점(한 채팅)**에서만, 바뀌면 **전 모듈 재로드·재테스트**(§8.1). 변경이 잦아지면 별도 'core' 채널 분리 재검토.

### 5.2 클라이언트 ↔ 서버 복본 동기화 규약 (v1.9.0 신설)

> **왜 필요한가.** §5.1·§8.1의 "복사 금지·단일 지점 변경"은 **클라이언트 안에서의** 재-인라인을 막는 규칙이었다. 그런데 §6.7의 서버화 결정으로 같은 계산 모듈이 클라(`assets/js/`)와 서버(`supabase/functions/_shared/`)에 **두 벌** 존재하게 됐다 — v1.4.0에서 모듈화로 없앤 '같은 버그를 두 번 고친다'가 **배포 경계를 넘어 되돌아온 형태**다. 빌드가 없어(정적 호스팅 + Deno Edge) 번들러로 합칠 수 없으므로 **규칙과 기계적 검사**로 막는다.

**규칙 1 — 정본은 언제나 클라이언트 `assets/js/`.** 서버 `_shared/`에 있는 같은 이름의 파일은 **복본**이다. 로직 수정은 정본에서 하고 복본에 옮긴다. **서버에서 먼저 고치는 방향은 금지** — 실제 드리프트가 그 방향으로 났다(아래).

**규칙 2 — 복본은 "정본 원문 + ESM export 꼬리"만 다르다.** 복본은 정본을 **바이트 그대로** 복사하고 파일 끝에 아래 두 줄만 덧붙인다. 그 외 어떤 차이도(주석·포매팅 포함) 허용하지 않는다.

```js
// [서버 전용] ESM named export
export const <ns> = globalThis.CubeNest.<ns>;
```

**규칙 3 — 검증은 `diff`로 한다(눈검사 금지).** 일치 여부는 기계적으로 확인된다:

```bash
diff -u assets/js/cubenest-<m>.js supabase/functions/_shared/cubenest-<m>.js
# 허용되는 차이 = 마지막 export 블록뿐. 그 외 한 줄이라도 나오면 드리프트다.
```

커밋 전에 손댄 모듈에 대해 이 명령을 돌리고, 결과를 해당 `<모듈>_기능개발명세서` 변경 이력에 적는다(§8.1 커밋 절차).

**규칙 4 — 클라가 로드하지 않는 모듈은 복본을 두지 않는다(서버 단일본).** 두 벌 유지 비용은 **양쪽이 실제로 쓰일 때만** 정당하다. 어느 페이지도 `<script src>`로 읽지 않는 클라 파일은 **죽은 사본**이고, 죽은 사본은 아무 증상 없이 갈라진다. 신규 서버 전용 계산 모듈은 처음부터 `_shared/`에만 만든다(`cubenest-hidden.js`가 그 예).

**현재 상태 (2026-08-20 실측):**

### 6.1 기술 스택 (서버리스)
- **프런트:** GitHub Pages(정적 HTML) — 서버·비밀키를 둘 수 없다.
- **백엔드:** **Supabase** — Auth(OAuth) · Postgres(+RLS) · Edge Functions(서버 로직·비밀키) · Storage.

### 6.2 인증 — Supabase OAuth 전용
- **OAuth 전용**(비밀번호 미사용): Google·Apple·**Kakao(한국 학부모 대상 1순위)**. 네이버는 커스텀 연동 검토.
- 로그인 주체는 **성인(교사·학부모) 중심.** 학생은 **무로그인 사용 유지**(아동 개인정보 최소화, 만14세 미만 규제 회피).
- **두 종류의 게이트를 구분한다:**

  - **하드 게이트(RLS):** 저장 데이터는 **Supabase Row Level Security**로 "본인 데이터만" 서버에서 강제. **실제 방어선.**
- **구현 현황 (v1.7.0):** 공용 인증 모듈 **`assets/js/auth.js`**(전역 `CubeNest.auth`)가 로그인 상태의 **단일 진실(`isLoggedIn`)**. **OAuth 전용·PKCE·localStorage 세션 지속**(멀티 페이지 오리진 공유). 공용 **로그인 모달(카카오·구글)** · 헤더 `#authNav` 라벨 자동 전환 · **`/account`** 페이지. 복귀 URL은 `code/state/error`만 제거하고 **`?m=`(playground)·`?seed=`(quiz)는 보존**. 로그인 실패 시 진단 로그 + `login_error` 계측. **구글·카카오 모두 실사용 검증 완료(v1.7.1).** 종전 모의(`cubenest_mock_login`) 제거.

### 6.3.1 calc 타임게이트 (결정)
- **목적(이중):** 회원가입 유도 + **숙제 치팅 방지.** 계산이 즉시 나오면 아이가 스스로 세어보지 않게 되며, 실제 아동 테스트에서 "치팅하는 느낌"이라는 피드백을 받았다. 타임게이트는 '먼저 스스로 세어본 뒤 계산으로 확인'하게 하는 교육적 장치이기도 하다.
- **30분의 정의:** **playground 페이지에서 첫 상호작용 시점부터의 경과 시간** 30분(탭만 열어둔 시간은 배제 지향, 누적 조작 시간까지는 아님).
- **대상:** **calc div만** 잠근다. 편집·관찰·위앞옆·층·공유 등 나머지 기능은 30분 이후에도 무료로 유지한다(무로그인 체험 원칙).
- **동작:** 30분 후 calc를 **완전히 잠그고** 회원가입·로그인을 유도한다. 단 **배너 톤은 부드럽게**(강압적이지 않게, 초등 톤).
- **리셋 정책:** 카운트는 **`localStorage`(오리진·기기·브라우저별)** 에 저장하고, **로그인하면 즉시 해제**한다. (브라우저·저장소를 비우면 초기화되는 등 우회는 가능하나 목적이 완벽 차단이 아니므로 수용. 하루 뒤 재부여 여부 등 세부는 구현 채팅 재량으로 열어둔다.)
- **성격:** 여전히 클라이언트 소프트 게이트다. 목적이 유도·교육이므로 서버 검증까지는 하지 않는다(과잉).
- **구현(v1.7.0):** 실제 로그인 연동 — 로그인 시 즉시 해제(모의 자리표시자 제거). **세션 복원 전에는 잠그지 않아 잠금 깜빡임 방지.** (quiz/run 첨삭 잠금도 동일하게 실제 로그인에 연결, 로그아웃 시 첨삭 모드 즉시 종료.)

### 6.4 저장 · 신원 추상화
- **로컬 우선 → 로그인 시 클라우드(Supabase) 동기화.** `save/load`를 얇은 인터페이스로 추상화해 교체 가능하게 둔다.
- 모양은 **직렬화(F2)** 로 문자열 하나로 저장·복원. `/my`는 **저장한 퀴즈 기록·문제지/정답지·모양**을 모은다. 공용 데이터 계층은 **`assets/js/mydata.js`**(로컬 우선, `/my`가 오너·account 소비) — 클라우드 동기화 시 이 계층만 교체.
- **재현 가능한 산출물은 본문을 저장하지 않는다 (v1.8.7).** 퀴즈·문제지는 **`(유형·난이도·seed) → URL`** 만 남기고, 열 때 서버가 같은 것을 다시 만든다. 저장 용량·동기화 비용이 사실상 0 이고, 정답지처럼 게이트가 필요한 산출물도 **열 때마다 로그인·이용권을 다시 통과**한다(정답지 본문을 로컬에 방치하지 않는다).
  - 목록 항목의 **id 는 그 URL 에서 결정적으로** 뽑는다. 안 그러면 같은 산출물을 열 때마다 사본이 쌓인다.
  - `meta.url` 이 있으면 `mydata.list()` 가 `openUrl` 로 승격한다(`/my` '열기' 버튼의 단일 조건).
  - 예외: **아이의 연습장 필기**는 재현 불가능한 원본이라 반드시 저장한다(6.4.1 `quiz_results.scratch`).

### 6.4.1 저장 스키마 · RLS 규약 (DB 착수 전 확정)

> 리포에 RLS 전례가 없어 **첫 마이그레이션이 곧 전례**가 된다. 아래는 착수 전 검토에서 확정한 방어선으로, 페이지·모듈이 재정의하지 않는다.
> **이름 확정:** 데이터 계층 = **`CubeNest.mydata`**(모듈 `assets/js/mydata.js`, §5.1), 클라우드 저장 테이블 = **`my_items`**(+ `quiz_results`·`profiles`·`entitlements`). (브리프의 `store`/`saved_items` 표기는 폐기.)

**행 생성 · 신원**
- `profiles` 행은 `auth.users` insert **트리거(`security definer`)로 자동 생성**한다. 클라이언트 upsert 경로는 사용자가 앱을 안 열면 행이 영영 안 생긴다.
- `profiles.role`(parent/teacher)은 self-assign이 가능하므로 **권한 판정에 쓰지 않는다** — 표시용 라벨. 권한은 RLS·서버가 판정한다(§6.2·§6.5).
- 모든 사용자 테이블: `user_id uuid not null references auth.users(id) on delete cascade default auth.uid()`.

**멱등성 · append-only**
- 결과 저장은 덮어쓰기가 아니라 **누적**이다. `quiz_results.attempt_id uuid not null` + `unique(user_id, attempt_id)`.
- `attempt_id`는 **세션 시작 시 클라이언트가 발급**해 진도 객체에 함께 보관하고, '다시 풀기'는 새 시도이므로 **새 `attempt_id`**를 발급한다.
- 저장은 `upsert(onConflict:'user_id,attempt_id', ignoreDuplicates:true)`. 멱등키가 없으면 "실패 vs 성공했는데 응답만 유실"을 구분 못 해 재시도가 곧 중복이 된다.

**무엇을 올리지 않는가**
- **진도(퀴즈 세션)·연습장 필기는 100% 로컬 전용.** 클라우드엔 **완료된 결과만, 사용자가 저장을 눌렀을 때만.** 충돌 규칙을 만드는 대신 **충돌 가능 상태 자체를 없앤다**(문제를 seed로 재현하는 현재 설계가 이미 "진도=기기 로컬 휘발성"). 잃는 것=기기 간 이어풀기 / 얻는 것=병합 UI·타임스탬프 신뢰·두 탭 경합 소멸. `/my`의 '다시 풀기'는 진도 복원이 아니라 **seed URL로 새 시도 시작**.
- **유일한 예외 = pending intent 재개:** 비로그인으로 저장을 누르고 로그인하면 **그 1건만** 자동 저장(그 외 자동 업로드 없음).
- **연습장 = 좌표 벡터(획 배열) (벡터 전환 완료, v1.8.2):** 획을 `{c,w,e,p:[[nx,ny]..]}` **정규화 좌표**로 저장하고 캔버스 크기가 바뀌면 재생한다(해상도 무관·리사이즈 무손실). 문항당 ~12KB(PNG 55KB)라 **`quiz_results.scratch jsonb`에 벡터를 그대로 담을 수 있다**(별도 Storage·이미지 업로드 불필요). 되돌리기 무제한(획 pop). **레거시 PNG dataURL 연습장은 `load()`에서 무시**(크래시 없이 빈 연습장으로 시작). ※ 단, **DB 착수 첫 마이그레이션에서는 여전히 `scratch`를 쓰지 않고 컬럼만 두는 것을 권장**(스키마 구축과 연습장 저장을 한 커밋에 섞지 않음) — 저장 배선이 안정된 뒤 벡터를 연결한다. Storage 버킷은 진짜 래스터가 등장하기 전까지 불필요.

**스키마 방어선**
- 목록에 필요한 필드는 `payload` 밖 **실컬럼으로 승격**(`title`·`kind`·`seed`·`type`·`n`·`score`·`created_at`).
- **`select *` 금지, 컬럼 명시 필수**(`.select('id,kind,title,score,created_at')`) — 안 지키면 승격이 무의미. 코드 리뷰 체크 항목.
- **`check (octet_length(payload::text) < 262144)`** — CHECK는 TOAST 이전 원문 바이트로 평가되어 정확한 예산. 클라이언트 버그가 DB를 못 망가뜨리게 하는 최후 방어선.
- **`payload`에 인덱스 금지.** 인덱스는 `<table>_user_id_created_at_idx`만.

**RLS 정책 컨벤션 (첫 전례)**
- 테이블당 **4정책(select/insert/update/delete), `to authenticated` 명시.** insert/update는 **`with check`** 필수.
- `auth.uid()`는 **`(select auth.uid())`로 감싸** initplan 캐싱(Supabase 권장).
- **`entitlements`는 사용자에게 `select`만.** insert/update/delete 정책을 주지 않는다(정책 0개=차단) — 사용자 self-grant 방지. **쓰기는 결제 Edge Function(service_role) 전용**(§6.5·§6.7).

### 6.5 결제 · 수익화
- **단계적 접근:** 베타 **전면 무료**(수요·피드백 검증) → 정식화 시 **기간 이용권(단건결제, 예: 30일권)부터**(결정). 자동갱신·정기결제 심사·cron·재시도 로직을 회피해 "학부모가 실제로 돈을 내는가"만 먼저 검증 → 수요 확인 후 **월 자동결제(빌링)로 확장**(그 단계에서 Supabase Pro).
- **구현 원칙:** 이용권 상태(만료일 등)는 Postgres에 저장, 결제 승인은 Edge Function(시크릿 키). **유료 접근 판정은 서버/RLS에서** — 클라이언트 신뢰 금지. **`entitlements` 테이블은 사용자 `select`만, 쓰기는 결제 서버(service_role) 전용**(RLS 규약은 §6.4.1).
- **유의:** 토스 **정기결제는 계약·카드사 심사**가 필요(정기결제용 상품 전제)하고 **PG 수수료**는 별도다. 환불·청약철회 정책을 약관에 명시. 결제자는 성인, 자녀 정보 최소화.

### 6.7 보안 · 지적재산 (IP 보호)

> **전제:** 정적 웹(GitHub Pages) + 브라우저 실행이라 **클라이언트로 내려가는 코드·데이터는 완전 은닉이 불가능**하다. 따라서 "기술로 100% 차단"이 아니라 **법적 보호 + 기술적 마찰 + 핵심 자산 서버화 + 유출 추적**을 겹쳐 쌓는다.

- **층 1 — 법적 보호(핵심·저비용):** 코드·문항·정답·해설은 작성 시점부터 자동 저작권. 저장소·산출물에 **저작권 표시**(© 사업자명·연도)와 **독점 라이선스**("All rights reserved, 무단 복제·재배포·역설계 금지") 명시. **이용약관**으로 크롤링·스크래핑·자동 수집·상업적 재사용·문항 복제 금지. 핵심 산출물은 **한국저작권위원회 저작권 등록**, 브랜드는 **CubeNest 상표 출원**(교육 서비스류).
- **층 2 — 기술적 마찰:** 배포 JS 난독화·minify, 소스맵 제외. 저장소 private·산출물만 공개. 생성기·config에 난독화 집중(완전 차단이 아니라 '베끼기 비용' 상승).
- **층 3 — 핵심 자산 서버화(가장 확실):** 독점 가치가 큰 자산을 클라이언트에서 빼 **Supabase Edge Function**으로 옮긴다. 클라이언트는 결과 인스턴스만 요청·수신(원본 로직 미노출). 유료 접근 판정은 서버/RLS(6.2·6.5).
- **층 4 — 유출 추적·억지:** 문항·워크시트에 계정·발급 시각 기반 워터마크·식별자. 대량 자동 수집은 Edge Function **rate limit·접근 로그**로 탐지·차단.

**정답 은닉 규약 (2026-08-17 확정 · quiz 검수 11):**
- **`/generate` 응답에 정답을 담지 않는다.** 종전엔 `q.correct`(facesMc 정답 번호)·`q.rc`(min/max)·`q.kinds`(A-f 정답)가 그대로 나갔다 — JSON에서 숫자 하나만 읽으면 답이 되는 상태였다. `present`(모양 중복 전송)도 폐지.
- **채점·색칠·해설의 단일 출처 = `/grade` 응답의 `answerKey`·`explain`.** 클라는 정답을 재계산하지 않는다(재계산하려면 모양을 들고 있어야 해서 은닉이 원천적으로 불가능해진다). **로컬 폴백 채점 없음** — `/generate` 없이는 세션이 시작조차 안 되므로 지킬 오프라인 세션이 없다. 실패 시 문항 미소진·재시도.
- **제시물만 전송(`given`):** 3D 회전이 풀이에 불필요한 유형(minmax·hidden)은 모양(`sh`) 대신 `given`을 받는다. `given.kind` = `sils`·`numTop`·`layers`·`isoTop`(겨냥도는 서버가 `cubenest-iso`로 그린 SVG).
- **[한계·수용] 3D 회전 유형은 은닉 불가.** count·volume·surface·heightmap·facesMc·facesDraw는 **돌려서 가려진 나무를 확인하는 것이 곧 풀이 과정**이라 형상이 클라에 있어야 한다. 이 6종은 직접 정답 필드만 제거한다.
- **[원리] 그림이 답을 정하는 유형은 그림을 주는 것이 은닉의 최선이다.** '안 보이는 나무' A-a/b/f의 답은 **보이는 그림만의 함수**다(숨은 열의 실제 높이는 어느 답에도 쓰이지 않는다). 따라서 서버 SVG에 가려진 큐브 좌표가 남아도 답이 새지 않으며, 치터도 학생과 똑같이 그림을 분석해야 한다.

- **무료 vs 보호 조율:** quiz 플레이는 무료(6.3)라 전면 서버화 시 무료 경험이 깨진다 → **유료·고가치(워크시트 정답지·대량 문항·특정 세트)는 로그인·이용권 후 서버 생성**, **무료 quiz는 서버가 요청당 1문항 생성(rate limit·익명+IP)**. 필요 시 무료용 경량 생성기 / 유료용 서버 전용 풀 생성기로 이원화.
- **주의:** 상표 출원·저작권 등록·약관 문구의 최종 확정은 변리사·IP 전문 변호사 확인 필요(본 절은 전략 방향).

**서버 이전 배포 현황 (2026-08-15) — P0.5 완료 ✅**
- `gen`·`gen-config`를 Supabase **Edge Functions**로 이전 완료 — **`/generate`**(문제 인스턴스, 정답 미포함) · **`/grade`**(서버 채점 + answerKey·해설). 원본 `cubenest-core`·`cubenest-gen`을 무수정 import, `gen-config`는 서버 상수화.
- **정적 `cubenest-gen.js`·`gen-config.json` 삭제 완료 — 생성기가 클라이언트에서 완전히 사라졌다.**(§2.1 트리·§9 인덱스에서도 제거.) 클라이언트는 `api-client.js`로 서버 `/generate`·`/grade` 호출.
- **`gsig`(HMAC-SHA256)** 로 채점 위·변조 방지, **Postgres rate limit**(익명 쿠키 + IP, `/generate`)로 남용 차단. **`/grade`는 rate DB 왕복을 제거하고 gsig 검증만으로 처리해 지연을 완화**한다. 현재 `verify_jwt=false` — 무료·익명 플레이라 **인증이 아니라 rate limit + gsig로 보호**한다. 유료·이용권 단계에선 이 엔드포인트에 로그인·entitlement 검증을 추가한다(6.2·6.5).

## 8. 공통 규칙

- **버전 관리:** 주(기능·핵심 규칙) / 부(세부 보완) / 수(문구). **문서마다 독립 버전·독립 변경 이력.** (문서 **버전**과 산출물 **파일명**은 별개다 — 아래.)
- **산출물 파일명 (v1.1.0 변경):** 개발 **흔적(작업 스냅샷)**은 `<모듈>_YYMMDD_NNNN`(확장자는 형식에 따름, 예 `.html`). `<모듈>` = `playground`·`quiz`·`worksheets`·`landing`·`guide` 등. 예) `playground_260729_0001`. **`NNNN`은 모듈별로 그날 0001부터** 매긴다(채팅을 모듈별로 분리하므로 각 채팅이 자기 번호를 독립적으로 부여 — 모듈 공통 연속번호는 조율 불가하여 채택하지 않음).
- **흔적 ≠ 배포 파일명:** 위 흔적 파일은 채팅 내 이력용이고, **리포에 커밋될 때는 해당 모듈 폴더의 `index.html`로 이름을 바꿔** 넣는다(예: `playground_260729_0007.html` → `playground/index.html`). URL·경로는 배포 파일명 기준(2.1).
- **브랜드 언어 전환:** `navigator.language`가 ko → '큐브네스트', 그 외 → 'CubeNest'(문서 제목 동일). 모든 페이지 공통.
- **경로·링크 (v1.1.0):** 프로젝트 페이지 하위경로(`/cubenest/`)이므로 **상대경로만** 사용(2.1). 루트 절대경로 금지.
- **페이지별 메타 (v1.1.0):** 각 페이지는 자기 URL로 `canonical`·`og:url`을 지정하고, `og:image`는 공용 `assets/img/cubenest-og.png`를 **절대 URL**(`https://smallhamsters.github.io/cubenest/assets/img/cubenest-og.png`)로 공유한다.
- **오리진 공유 상태 (v1.1.0):** `localStorage`(동의 키 `cubenest_consent`)와 GA4는 **경로가 아니라 오리진(`smallhamsters.github.io`) 단위로 공유**된다. 따라서 모든 페이지가 **같은 `GA4_ID`와 동일한 opt-in 동의 스니펫**을 써야 한 번의 동의가 사이트 전체에 적용되고 계측이 한 속성으로 합쳐진다.
- **공용 자산 (v1.2.0):** OG 브랜드 카드(`assets/img/cubenest-og.png`)·글리프(`assets/img/brand-glyph.svg`)·공용 CSS(`assets/css/`: `tokens.css`·`consent.css`·`nav.css`·`auth.css`)·공용 JS(`assets/js/`: `consent.js`·`auth.js`·`mydata.js`)는 리포 **`assets/`**(css·img·js) 아래에 둔다. 브랜드 토큰(워드마크·액센트색 `#3f3fbf`)은 `tokens.css`를 단일 출처로 페이지 간 동일해야 한다.

### 8.1 모듈별 채팅 분리 · 동기화 (v1.1.0)

기능 모듈(playground·quiz·worksheets·landing)을 **각각 다른 채팅에서 개발**한다. 표준적인 모노레포+모듈 오너십 구조이며, 유일한 위험은 **공용 자산의 동기화**다. 아래 규칙으로 관리한다.

- **모듈 ↔ 문서 매핑:** 커밋 지점에서 갱신하는 스펙 문서는 모듈마다 정해져 있다 — playground → `playground_기능개발명세서`, worksheets → `worksheets_기능개발명세서`, landing → `landing_기능개발명세서`, quiz → `quiz_기능개발명세서`, guide → `guide_기능개발명세서`, account → `account_기능개발명세서`, my → `my_기능개발명세서`. (마스터만 `CubeNest_00_마스터_공통`.)
- **마스터는 단일 지점에서만 변경:** 3·4장([불변])을 여러 모듈이 참조하므로, 마스터 수정은 **한 번에 한 곳(한 채팅)**에서만 하고, 마스터가 바뀌면 각 모듈 채팅은 **최신 마스터를 다시 읽고** 시작한다. 모듈 문서는 "마스터 ○장 참조"만 하고 **재정의 금지**.
- **공용 로직은 공용 모듈 import (v1.4.0 개정):** F1~F5·§4 계산·3D 뷰어·펼쳐보기는 **`assets/js/cubenest-*.js` 공용 모듈로 두고 각 페이지가 참조(import)** 한다(§5.1). **재-인라인·복사 금지.** playground가 최초 추출 출처이자 첫 소비자(도그푸드). 모듈 변경은 **단일 지점(한 채팅)**에서만 하고, 바뀌면 **전 모듈이 다시 로드·테스트**한다. 공용 모듈 API 변경은 [불변] 수준의 파급이므로 신중히 한다. (전환 전까지 quiz·worksheets의 **신규 인라인 복사는 보류**.)
- **공용 헤더(HTML 마크업) — 위 '재-인라인 금지'의 예외 (v1.8.0):** 위 규칙은 **JS 공용 로직에만** 적용된다. 공용 상단 헤더는 **스타일만 `assets/css/nav.css` 단일 출처로 공유하고, 마크업은 각 페이지 HTML에 인라인**으로 둔다. 빌드 없는 정적 호스팅이라 서버 인클루드가 없고, 헤더를 JS로 주입하면 2차 렌더로 밀려 내부 링크 발견이 늦고(SEO 손해), iframe은 링크가 iframe URL로 귀속돼 둘 다 손해다. **드리프트 방지:** `account/index.html`의 헤더(`.site-topin` 전체 — `.site-nav` + `.site-actions`)를 **정본**으로 삼아 복사하고 **경로·`aria-current`만** 바꾼다. **메뉴 6종(홈·가이드·플레이그라운드·퀴즈·문제지 생성·내 자료)은 전부 `.site-nav` 안의 텍스트 링크**이고, 우측 `.site-actions` 에는 **계정 아이콘 하나만** 둔다 — 목적지가 있는 페이지 이동은 메뉴이고, 아이콘 축약은 무엇인지 알 수 없어 오히려 못 찾는다(v1.8.8).
- **클라↔서버 복본은 §5.2를 따른다 (v1.9.0):** 같은 계산 모듈이 `assets/js/`와 `supabase/functions/_shared/`에 두 벌 있는 경우, **정본=클라 · 복본=원문+ESM export 꼬리 · 검증=`diff`** 이고 **클라가 로드하지 않는 모듈은 복본을 두지 않는다.** 위 '재-인라인 금지'가 클라 내부의 규칙이라면, §5.2는 같은 원칙을 **배포 경계 너머로** 확장한 것이다.
- **페이지 문서는 최신 마스터를 다시 읽는다 (v1.9.0 보강):** 각 `<모듈>_기능개발명세서` 헤더의 **'기준 마스터: vX.Y.Z'** 는 그 문서를 마지막으로 손볼 때 읽은 마스터 버전이다. 모듈 작업을 시작할 때 이 값이 §9의 현재 마스터 버전보다 낮으면 **먼저 마스터를 다시 읽고 헤더를 갱신한 뒤** 시작한다. 값이 뒤처져 있다는 것 자체가 "이 문서는 최신 공통 규칙을 모른 채 쓰였다"는 신호다.
- **커밋 절차:** 채팅에서 흔적(`<모듈>_YYMMDD_NNNN`)으로 개발 → 커밋할 지점 확정 → 그 산출물을 배포 파일명(`<모듈>/index.html`)으로 리포에 넣고 → **공용 모듈을 손댔으면 §5.2 규칙 3의 `diff` 실행**(결과를 변경 이력에 기록) → 해당 `<모듈>_기능개발명세서` 갱신(헤더 '기준 마스터' 포함) → 마스터 9장 인덱스 표의 버전 갱신.
